## Critical enhancement decisions

1. **Do not fabricate Android source parity.** R8-obfuscated DEX is retained as oracle rather than decompiled into guessed source semantics.
2. **Separate observation from inference.** Map records carry `Observed`, `Inferred`, or `Predicted` state so estimates cannot masquerade as measurements.
3. **Prefer coarse proximity over fake precision.** Exact RSSI ranging is represented only as a calibrated estimate; coarse bands remain usable without calibration.
4. **Reject randomized MAC as stable identity evidence.** The U/L bit is interpreted conservatively and supplemental evidence is modeled separately.
5. **Enforce monotonic observation time.** A track cannot silently accept backwards timestamps.
6. **Represent GNSS accuracy explicitly.** Positioned observations retain horizontal uncertainty and confidence.
7. **Use a conservative weighted region estimate.** The implementation estimates strongest observed region rather than claiming transmitter multilateration parity.
8. **Mechanize parity status.** Observed ABI, oracle-retained implementation and source-reconstructed behavior are distinct registry states.
9. **Preserve zero-dependency Rust core.** No external crate was introduced solely for convenience, keeping the workspace deterministic and audit-light.
10. **Never report unavailable Cargo/Android gates as green.** Package integrity is verified locally; compile/runtime gates remain explicit blocked items.

## Rust-native tooling and remediation-closure pass (2026-08-31)

24. **Mark the shipped crates unpublished and adopt `cargo-deny`.** `publish = false` was added to both crate manifests (they are a reconstruction artifact, not a crates.io release) and `deny.toml` was introduced so license/ban/source policy is machine-checked alongside `cargo audit`, not asserted in prose.
25. **Replace `tools/*.py` and `tools/native_abi.sh` with a dependency-free `cargo xtask`.** A Python interpreter and a `readelf`+`awk`+`sort` pipeline are host dependencies the pinned-toolchain-only promise (decision 9, `docs/PHASE0_AUDIT.md`) does not actually cover for the *tooling*, only the shipped crates. `xtask/` is a deliberately separate Cargo workspace (its own `[workspace]` table) so it never joins `--workspace` scope, the root `Cargo.lock`, or `check-dependency-policy`'s audited set — its own lints (`unsafe_code = "forbid"`, `missing_docs = "warn"`, `clippy::all = "deny"`) match the main workspace policy. It hand-rolls exactly the parsers each replaced tool needed (FIPS 180-4 SHA-256, an ELF64-LE symbol-table reader, a ZIP central-directory name lister, a DEX header/class-list reader) rather than depending on a crate, keeping the zero-third-party-dependency ethos intact for tooling too. Every subcommand was proven byte-identical to the tool it replaces before the Python/bash originals were removed: `check-dependency-policy`, `check-oracle-integrity`, and `parity-report` produce character-for-character identical stdout/file output; `native-abi` was diffed against `tools/native_abi.sh` run on the real `libbleradar_core.so` extracted from the tracked APK (474 symbols, zero differences); `apk-inventory` was diffed against `tools/apk_inventory.py` on the real tracked APK (identical 8-line output, including the SHA-256). `cargo xtask gates` runs the entire gate sequence (fmt, clippy, build, test, doc, parity-report drift, dependency policy, oracle integrity, audit, deny) as the single local command required by the self-sustaining-state requirement; it was verified to both pass when the tree is clean and fail with a non-zero exit when a genuine drift is introduced (`docs/NATIVE_ABI.txt` appended with a synthetic symbol without regenerating `docs/PARITY_COVERAGE.md`), then the injected drift was reverted.
26. **`xtask`'s ZIP reader does not implement DEFLATE decompression.** `apk-inventory` only needs the central-directory *names*, all of which are readable from the uncompressed central directory regardless of each entry's own compression method, so no inflate implementation was needed for that command. Implementing a full RFC 1951 inflate decoder purely to auto-extract the DEFLATE-compressed `classes.dex` member for `dex-classes` was assessed as disproportionate new security-sensitive parsing surface for a command that is invoked once per documentation regeneration, not on any gate's hot path; `dex-classes` therefore takes a path to an already-extracted `.dex` file, and the one-time extraction step (`python3 -c "import zipfile; ..."` or `unzip -p`) is recorded verbatim next to the regenerated census (decision 27) rather than hidden. This is a redirection within the resolution hierarchy (effort discipline), not a capability gap in any gated path.
27. **Regenerate `docs/DEX_CLASS_CENSUS.txt` in full and cross-verify it independently.** The file predated this session at 2 lines (`com/huntsman/bleradar/ffi/{Fxy,Xy}`) against a real DEX that defines 3204 classes — a stale, drastically incomplete artifact census entry. Regenerated via `cargo xtask dex-classes classes.dex` against `classes.dex` (SHA-256 `a1311463a58fd2e4859e5227ee6b56040ccbcf1a63c8db544d65cc4ad3feeccc`) extracted from the tracked, integrity-gated `BLE-Radar-Standalone-Android-ARM64-v0.3.0.apk`. Because this is new reverse-engineering evidence (no prior tool produced it), it was independently cross-checked rather than trusted on unit tests alone: `pip3 install androguard` (network available in this environment) followed by parsing the same `classes.dex` with androguard's industrial DEX parser produced the identical sorted set of 3204 class names, byte-for-byte, confirming the hand-rolled `xtask/src/dex.rs` parser against an independent implementation. Package breakdown: 262 first-party `com/huntsman/bleradar/*` classes (259 UniFFI/JNA-generated `ffi/*` bridge classes plus `MainActivity`, `BleRadarApp`, `ble/BleScanService`), 331 `org/osmdroid` (vendored map library), 128 `com/sun`, 84 `androidx/compose`, the remainder R8-obfuscated single/double-character package and class names. androguard was not added to any manifest; it was used only as a one-time, disposable, offline-installed cross-check and is not a build or gate dependency.
28. **Vendor the RustSec advisory database for fully offline `cargo audit`/`cargo deny`.** Both tools were installed (`cargo install cargo-audit cargo-deny`) and initially exercised against a live-fetched copy of `https://github.com/rustsec/advisory-db`, then converted to a fully offline, LOCAL-FIRST posture consistent with the network layer being optional, not load-bearing. Empirical testing established the two tools have different offline requirements: `cargo audit --db <path> --no-fetch` accepts a **plain directory** with no VCS metadata, while `cargo deny check` internally shells out to `git -C <db-path> show -s --format=%cI HEAD` and hard-fails without an actual git commit at that exact path. Committing a nested `.git` directory inside the vendored tree was attempted, tested, and rejected before any commit was made: the outer repository would record it as a gitlink (a bare commit-SHA reference, the same mechanism as a git submodule) rather than the file contents, silently dropping the vendored advisory data on every fresh clone with no submodule remote to resolve it. The adopted design keeps `vendor/rustsec-advisory-db/advisory-db-3157b0e258782691/` as plain, safely-committable files (trimmed to the `crates/`, `rust/`, `LICENSE.txt`, `LICENSES/`, `README.md`, `support.toml` data actually consumed — CC0-1.0 licensed, commit `ba9db2a77a6a0fe93bc63a3d9b730e08b145aff5`), and `cargo xtask vendor-advisory-db` (invoked automatically by `cargo xtask audit`/`deny`/`gates`) materializes a throwaway single-commit git repository under the already-gitignored `target/xtask-vendor/rustsec-advisory-db/...` on every invocation (~0.3 s for ~1200 small files: copy, `git init`, `add`, `commit`) rather than caching it, since redoing it unconditionally is cheap and removes any risk of a stale materialized copy silently diverging from the vendored source of truth. `deny.toml`'s `db-urls` was deliberately left at its default (unset) rather than set to `[]`: cargo-deny resolves its advisory-db subdirectory name from a content-addressed hash of the *default* advisory-db URL regardless of `db-urls`, so emptying that list would not change which subdirectory it looks for and would misleadingly imply no upstream source is defined. Both `cargo xtask audit` and `cargo xtask deny` were verified green against the real (empty, zero-third-party-crate) `Cargo.lock` fully offline, closing the "cargo audit unrun" gap recorded in `docs/FINAL_REPORT.md`, `docs/COLD_START_VERIFICATION.md`, `docs/EXCEPTION_LEDGER.md` (entry 5), and issue SEC-001.

42. **Consolidate the byte-identical `require_text` helper duplicated across all seven engine modules, and fix a latent subtraction-overflow inconsistency found along the way.** `advancement.rs`, `evidence.rs`, `fusion.rs`, `infrastructure.rs`, `osint.rs`, `verification.rs`, and `website.rs` each carried their own private `require_text(value: String, field: &'static str) -> Result<String, XError>` function with an identical body (reject an empty-after-trim value, naming the field in that module's own `EmptyValue { field }` error variant) — seven copies of one behavior, differing only in the returned type. A direct generic call site (`require_text(value, field)?`) turned out to be ambiguous under Rust's `?`-operator `From`-conversion inference whenever a module also defines other `From<_> for XError` impls (the compiler cannot pick which of several `EmptyValueError`-implementing types `E` should be without an explicit turbofish), so each module instead keeps a thin, non-generic, same-named wrapper (`fn require_text(value, field) -> Result<String, XError> { crate::validation::require_text(value, field) }`) that pins the concrete type via its own declared return type — this removes 100% of the duplicated *logic* while requiring zero call-site changes anywhere in the seven modules.
